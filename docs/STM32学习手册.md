## 01 学习终点定义

### 先说一个必须放弃的目标

**"学完 STM32"是做不到的，因为它没有终点。**

外设层（GPIO → 定时器 → 通信接口 → USB / 以太网 / CAN）→ 系统层（FreeRTOS → 文件系统 → 协议栈）→ 芯片层（F0/F1/F4/H7/G0/U5 各系列横向扩张）→ 应用层（电机控制、音频、低功耗、安全启动）。任意一条支线都能再走三年。

拿一个没有终点的目标当方向，结果必然是**无限延期 + 永远觉得自己没准备好**。

### 用可判定的终点替代它

本手册采用的终点定义（三条同时满足即达标）：

| # | 终点判据 | 怎么验证 |
| --- | --- | --- |
| 1 | **能脱离教程，独立写出一个多任务固件** | 给一个没做过的需求，能自己查参考手册把它实现出来 |
| 2 | **能讲清自己做的每一个技术取舍** | 被追问"为什么这么选"时，答案来自对比而不是记忆 |
| 3 | **有一套自己的调试方法论** | 遇到新问题知道按什么顺序排查，而不是靠试 |

> 这三条的共同点是：**它们都与"会多少外设"无关，而与"能不能自己往前走"有关。**
>
> 面试考的就是这三条。"会多少个外设"是最不重要的指标——因为手册上都有，查得到；而"为什么这么选、踩过什么坑、重做会改什么"查不到。

## 02 学习地图

### 四层结构

```
L0 工具链与心法（先解决，否则后面全是无效劳动）
 ├─ 编译 / 烧录 / 调试全链路
 ├─ 串口 printf 调试
 ├─ 逻辑分析仪抓波形
 └─ 三层学习法：寄存器懂原理 → HAL 做开发 → LL 做优化
        │
        ▼
L1 裸机外设（STM32 的主体，占比最大）
 ├─ GPIO ──→ EXTI ──┐
 ├─ RCC 时钟树（所有外设的前提）│
 ├─ NVIC 中断体系 ←────────────┘
 ├─ TIM 定时器 ──→ PWM 输出
 ├─ UART ──→ 阻塞 / 中断 / DMA 三种收发
 ├─ DMA（贯穿 UART / ADC / SPI）
 ├─ I2C ──→ 多器件共总线（引出互斥量需求）
 ├─ SPI ──→ 外部 Flash / 显示屏
 └─ ADC ──→ 定时器触发 + DMA 搬运
        │
        ▼
L2 FreeRTOS（从"能跑"到"跑得住"）
 ├─ 任务与调度
 ├─ 队列 / 信号量 / 互斥量 / 事件组 选型
 ├─ 优先级反转与优先级继承
 ├─ 中断安全 API（FromISR）与临界区
 └─ 栈溢出与堆管理
        │
        ▼
L3 应用层（项目驱动，不单独学）
 ├─ BSP / App 分层架构
 ├─ 自定义串口帧协议（帧头 / 长度 / 校验 / 状态机）
 ├─ LVGL 移植与界面
 └─ 低功耗（可选）
```

### 两条依赖关系（记这两条就够）

1. **RCC 是所有人的前提。** 任何外设不先开时钟就是不工作，且报错方式千奇百怪（不报错、没反应、偶发死机）。
2. **中断和 DMA 是横切关注点。** 它们不属于某个外设，而是给所有外设提速的手段。学的时候分开学，用的时候到处用。

### 学习顺序的三个原则

- **先跑通再理解。** 先让波形出来，再回头搞清为什么。反过来会卡死在概念里
- **一个外设 = 一个可验证的现象。** 不接受"我看懂了但没做"——没有现象就不算学过
- **每学一个新外设，都要用到已有的项目里。** 单独建一堆 `test1.c`、`test2.c` 的学习方式，三周后连自己都忘了哪个文件是什么

### L0 工具链与心法

#### 3.1 编译 / 烧录 / 调试全链路

| | |
| --- | --- |
| **学什么** | 从 `.ioc` 到板子上跑起来，中间经过哪些环节；每个环节出错时的典型现象 |
| **为什么重要** | 这是唯一一个"不学就完全无法开始"的知识点。工具链不通时，任何外设知识都用不上。而且它是最容易被误判成"环境问题"而浪费几天的地方 |
| **常见追问** | "你的工程怎么编译的？"——答"Keil 里点一下"和答"CMake 生成 Ninja 构建文件，arm-none-eabi-gcc 编译，ST-Link GDB Server 通过 SWD 烧录"，是两种档次 |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §01、§06 |
| **怎么验证** | 删掉 `build/` 目录，从命令行重新配置并编译出 `.elf`，再烧录成功——全程不看 IDE 界面 |
| **学会的标准** | 能画出这条链路：`.ioc` →（CubeMX）→ `CMakeLists.txt` + `Core/` + `Drivers/` →（CMake + Ninja）→ `build/Debug/*.elf` →（ST-Link GDB Server + SWD）→ 芯片。并且能说出任一环断掉时现象是什么 |

#### 3.2 串口 printf 调试

| | |
| --- | --- |
| **学什么** | `printf` 重定向到 UART 的原理（`_write()` / `fputc` 重定向）；为什么浮点输出默认是空的 |
| **为什么重要** | 这是嵌入式的"console.log"。逻辑分析仪看时序，串口看数据和状态——两者互补。不会串口打印，调试效率会低一个数量级 |
| **常见追问** | "`printf("%.2f")` 输出空白，是什么原因？"——GCC 默认关闭浮点 printf，链接时要加 `-u _printf_float`，同时确认 FPU 已开 |
| **怎么配** | CubeMX 里 USART1 → Asynchronous，115200 / 8N1；重定向代码放在 `BSP/` 下 |
| **怎么验证** | 串口助手能收到 `printf("Hello\r\n")`；`printf` 一个浮点数能正常显示（不是空白）；**动态观察**：在循环里打印一个递增值，确认不是只打印一次 |
| **学会的标准** | 能解释"为什么 `printf` 能打到串口上"（标准库的底层写函数被重定向了），能说出浮点不显示的两个原因（链接选项 / FPU）|

> **一条硬规则**：`printf` 在中断里调用会阻塞，绝不要在中断服务函数里用。要打印就在中断里置标志，回主循环再打印。

#### 3.3 逻辑分析仪抓波形

| | |
| --- | --- |
| **学什么** | 怎么接、怎么设触发、怎么读 I2C / SPI / UART 时序；入门款能抓到什么频率 |
| **为什么重要** | 它把"我以为它通了"变成"我确认它通了"。这是最便宜的一件设备（入门款几十元），但它带来的可信度提升不成比例 |
| **常见追问** | "你怎么确认 I2C 通信真的成功了？"——"读返回值是 0 就认为成功"和"我抓了波形，看到从机在第 9 个时钟拉低了 SDA，即 ACK 位有效，说明器件确实应答了"，完全不是一个水平 |
| **怎么配** | 见 `00-采购清单.md` 第三批。本项目要抓的 I2C ≤ 400 kHz、SPI ≤ 10 MHz，入门款够用 |
| **怎么验证** | 抓到一次 I2C 完整读时序，**截图存档**；抓到一次 SPI 的 CS / SCK / MOSI / MISO 四线时序；能指出图上哪个位置是 ACK、哪个位置是数据变化沿 |
| **学会的标准** | 拿到一段陌生波形，能判断：这是什么协议、时钟频率多少、从机有没有应答、数据是几字节 |

#### 3.4 三层学习法：寄存器 / HAL / LL

| | |
| --- | --- |
| **学什么** | 三个层级各解决什么问题，什么时候该往下钻 |
| **为什么重要** | 很多人卡在"到底该学寄存器还是学 HAL"这个伪选择题上。答案是**都要，但深度不同** |
| **怎么配** | 见第 04 章 |
| **怎么验证** | 任选一个外设（比如 GPIO 输出），能同时说出：① 用 HAL 怎么写 ② 直接操作哪个寄存器、哪一位 ③ 用 LL 怎么写 |
| **学会的标准** | 面试问"`HAL_GPIO_WritePin` 底层干了什么"时，能答出"写的是 `BSRR` 寄存器，`BSRR` 是置位/复位寄存器，写 1 到低 16 位置位、写 1 到高 16 位复位，这样做的好处是原子的，不需要读-改-写" |

### L1 裸机外设

#### 3.5 GPIO 输出与输入

| | |
| --- | --- |
| **学什么** | 输出模式（推挽 / 开漏）、输入模式（上拉 / 下拉 / 浮空 / 模拟）、速度等级、**为什么要先开 GPIO 时钟** |
| **不学什么** | 具体的寄存器位定义（用时查手册即可）、复用功能映射表（太长，需要时查） |
| **为什么重要** | HAL 把 GPIO 封装得最浅，所以它是唯一一个**必须理解到底层**的外设——面试问 GPIO 往往是在问时钟使能和 BSRR 原子性 |
| **常见追问** | ① 推挽和开漏的区别，什么时候必须用开漏（I2C、电平不匹配时）② 为什么 `HAL_GPIO_TogglePin` 是原子的（写 BSRR 而非读-改-写 ODR）|
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 1 项 |
| **怎么验证** | LED 以 1 Hz 闪烁（用 `HAL_Delay`）；按键能可靠触发（消抖后可长按计数）；**用万用表量引脚电平**，确认与代码预期一致 |
| **学会的标准** | 能不看代码说出：这个引脚配成了什么模式、为什么、对应原理图上的哪个器件；能解释"为什么我的 LED 不亮"的排查顺序（时钟 → 引脚号 → 极性 → 硬件接线）|

#### 3.6 RCC 时钟树

| | |
| --- | --- |
| **学什么** | HSE / HSI / PLL 的关系；AHB / APB1 / APB2 三级分频；**为什么 APB1 上的定时器时钟是 PCLK1 × 2** |
| **为什么重要** | 时钟是所有外设的隐含前提。配错时钟的典型现象是"串口乱码""`HAL_Delay` 时长不对""定时器频率差一倍"——而这些现象看起来都像是外设问题，极难定位 |
| **常见追问** | ① APB1 定时器时钟为什么要 ×2 ② 分频系数不为 1 时 ×2，为 1 时呢（不乘）③ 为什么 APB1 上限低于 APB2 |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §03。**先确认真实晶振频率**（板上通常丝印标明，或看原理图）|
| **怎么验证** | 用 `HAL_RCC_GetHCLKFreq()` / `HAL_RCC_GetPCLK1Freq()` 把实际频率打印出来，与 CubeMX 里的配置对照；再配一个 1 kHz PWM，用逻辑分析仪量实际频率是否吻合 |
| **学会的标准** | 给你目标主频，能在纸上推出 PLLM / PLLN / PLLP 的值，并算出各级总线频率；能说出"串口乱码先怀疑时钟"这条排查直觉 |

#### 3.7 NVIC 中断与优先级

| | |
| --- | --- |
| **学什么** | 中断优先级分组（Cortex-M 的抢占优先级 / 响应优先级）、优先级数值与优先级高低的关系（**数值越小优先级越高**）、中断服务函数的执行上下文 |
| **不学什么** | 不用背完整的中断向量表；不用一开始就学尾链优化、迟到中断这些 Cortex-M 细节 |
| **为什么重要** | 优先级配错会导致"偶发丢数据""中断里卡死"这类极难复现的问题。而且它是 FreeRTOS 的前置知识——RTOS 的调度完全建立在 PendSV 和 SysTick 中断优先级之上 |
| **常见追问** | ① 抢占优先级和子优先级的区别 ② 中断里为什么不能调用 `HAL_Delay`（它是基于 SysTick 的阻塞等待，而 SysTick 优先级通常低于你当前的中断，会直接死锁）③ FreeRTOS 为什么要把 PendSV 和 SysTick 设成最低优先级 |
| **怎么配** | CubeMX → System Core → NVIC，勾选所需中断线并设优先级；`NVIC.PriorityGroup` 决定分组 |
| **怎么验证** | 配两个不同优先级的中断，让高优先级中断打断低优先级中断，在各自服务函数里翻转不同引脚，用逻辑分析仪观察嵌套行为 |
| **学会的标准** | 能解释"为什么中断服务函数要尽量短"（会阻塞同优先级和低优先级中断）；能说出中断里绝对不做哪三件事（阻塞延时、动态内存分配、`printf`）|

#### 3.8 EXTI 外部中断

| | |
| --- | --- |
| **学什么** | 边沿触发（上升 / 下降 / 双边沿）与电平触发的区别；**EXTI 线号与引脚的对应关系**（同一时刻每个组只能有一个引脚作为 EXTI 源）；中断与事件的区别 |
| **为什么重要** | 它是按键、编码器、外部唤醒（低功耗）的共同基础；也是理解"中断上下文限制"的第一个实战场景 |
| **常见追问** | "为什么 PA0 和 PB0 不能同时做 EXTI？"——它们共享 EXTI0 线；"按键不加消抖会怎样"——一次按下触发多次中断 |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 2 项 |
| **怎么验证** | 按键触发 LED 翻转；**加软件消抖**后再测，对比抖动次数；用逻辑分析仪看按键波形里的实际抖动，理解为什么必须消抖 |
| **学会的标准** | 能说出"EXTI 中断里我只置一个标志位，实际处理放主循环"这个模式，并解释为什么 |

#### 3.9 定时器（基本定时 / 中断）

| | |
| --- | --- |
| **学什么** | PSC / ARR 的作用与自动重装载的含义；向上 / 向下 / 中央对齐计数模式；更新中断；**定时时间的计算公式** |
| **不学什么** | 编码器模式、输入捕获、从模式触发、死区——这些用到再说 |
| **为什么重要** | 定时器是嵌入式里最"万能"的外设：定时、延时、PWM、捕获信号、触发 ADC 都靠它 |
| **常见追问** | ① 给定定时时间怎么算 PSC 和 ARR ② 为什么 `HAL_Delay` 在 RTOS 里要换成 `vTaskDelay` ③ 定时器时钟到底是多少（回到 3.6 的 APB1 ×2）|
| **怎么配** | CubeMX → Timers → TIMx，Clock Source 选 Internal Clock，设 PSC / ARR，打开更新中断 |
| **怎么验证** | 配一个 1 Hz 中断翻转 LED，**再用逻辑分析仪量周期，误差应在晶振精度范围内**；改 PSC 或 ARR，重新推算并验证 |
| **学会的标准** | 不看代码，给出任意定时时间和一个定时器时钟，能算出 PSC / ARR 组合（并说出为什么这么取）|

#### 3.10 定时器 PWM 输出

| | |
| --- | --- |
| **学什么** | 频率与占空比分别由谁决定（频率 = 时钟 / ((PSC+1)×(ARR+1))，占空比 = CCR / (ARR+1)）；输出比较模式；极性配置 |
| **为什么重要** | PWM 是控制类应用（电机、调光、舵机、加热）的输出手段。而这条公式是面试的高频送分题，答不上来很吃亏 |
| **常见追问** | ① PWM 频率怎么算 ② 改占空比时改哪个寄存器、要不要停定时器（改 CCR 不用停）③ 死区是什么（进阶，FOC 会用到）|
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 3 项与 PWM 公式小节 |
| **怎么验证** | 驱动 LED 做呼吸灯（改 CCR）；**用逻辑分析仪量出实际频率和占空比**，与计算值对照而不是想当然 |
| **学会的标准** | 要 20 kHz、占空比 50% 的 PWM，能当场算出 PSC / ARR / CCR 三个值 |

#### 3.11 UART 三种收发方式

| | |
| --- | --- |
| **学什么** | 阻塞式（`HAL_UART_Transmit`）、中断式、DMA 式三者的取舍；**空闲中断（IDLE）+ DMA + 环形缓冲区**接收不定长数据的完整方案；粘包与断帧 |
| **为什么重要** | 这是"会不会写工程代码"的分水岭。只会阻塞式 `HAL_UART_Receive` 的人，一旦数据量上来就会丢数据，而答不出怎么改 |
| **常见追问** | ① 为什么轮询接收会丢数据 ② 为什么用空闲中断而不是逐字节中断 ③ 环形缓冲区解决什么问题、什么时候会溢出 ④ 如何从字节流里切出完整帧 |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 4、5 项 |
| **怎么验证** | 串口助手**高速连续发一长串不定长数据**，用 DMA + 空闲中断 + 环形缓冲接收，验证完整无丢包；再故意超长发送，确认溢出被正确检测而不是静默丢数据 |
| **学会的标准** | 能画出"数据到达 → DMA 搬运 → 空闲中断触发 → 通知任务处理 → 环形缓冲取帧"的数据流，并说出每个环节放弃会怎样 |

#### 3.12 DMA

| | |
| --- | --- |
| **学什么** | 为什么需要 DMA（CPU 搬运 vs 外设直连内存）；普通模式与循环（Circular）模式；什么是传输完成中断；DMA 与外设的请求映射关系 |
| **为什么重要** | 它是"性能"这个词在 MCU 上的具体落点。ADC 连续采样、UART 大量收发、SPI 刷屏都靠它。而且是面试里区分"学过"和"做过"的常用问题 |
| **常见追问** | ① DMA 传输时 CPU 在干什么 ② 循环模式和普通模式分别用在什么场景 ③ 缓冲区被 DMA 和 CPU 同时访问会怎样（引出 F7/H7 的 Cache 一致性问题，F1/F4 无此问题）|
| **怎么配** | 在对应外设（USART / ADC / SPI）的 DMA Settings 里添加请求，选模式与数据宽度 |
| **怎么验证** | ADC 用定时器触发 + DMA 搬运一批数据，串口打印出来；**对比开 DMA 与不开 DMA 时的 CPU 负载或最大可用采样率**，用数据说话 |
| **学会的标准** | 能解释"DMA 不是在省代码行数，是在省 CPU 时间"，并举出一个具体场景说明如果不用 DMA 会怎样 |

#### 3.13 I2C

| | |
| --- | --- |
| **学什么** | 起始 / 停止 / 应答机制；**7 位地址与 HAL 传参要左移一位**这个坑；标准模式 100 kHz 与快速模式 400 kHz；多器件共总线的寻址方式 |
| **为什么重要** | 传感器几乎全是 I2C。而这个外设是 HAL 抽象最"漏"的地方——地址左移这个坑几乎人人踩过，是面试里很好用的"踩坑故事"素材 |
| **常见追问** | ① SHT30 手册写 `0x44`，代码里为什么要写 `0x44 << 1` ② 同一总线上多个器件怎么区分 ③ 总线被拉死（时钟被从机拉低不放）怎么恢复 |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 6 项 |
| **怎么验证** | 读 SHT30 的序列号并与手册对照；**用逻辑分析仪确认第 9 个时钟有 ACK**；用 `HAL_I2C_IsDeviceReady()` 扫描总线地址 |
| **学会的标准** | 拿到一个不认识的 I2C 器件，能自己查手册找到地址、寄存器表、读时序，并写出读数据的代码 |

#### 3.14 SPI

| | |
| --- | --- |
| **学什么** | 四线（SCK / MOSI / MISO / CS）；**CPOL / CPHA 组成的四种模式**及如何从器件手册确定用哪种；全双工主从；片选时序 |
| **为什么重要** | 高速外设（外部 Flash、TFT 屏、部分传感器）走 SPI。四种模式配错是最典型的问题——代码全对但读出来全是 `0xFF` |
| **常见追问** | ① SPI 的四种模式怎么区分 ② 怎么从器件手册判断用哪个模式 ③ SPI 为什么比 I2C 快、代价是什么（引脚多、无应答机制）|
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 7 项 |
| **怎么验证** | 读 W25Q64 的 JEDEC ID，**应为 `EF 40 17`**——读到 `FF FF FF` 说明模式错或片选没拉低，读到 `00 00 00` 说明 MISO 没接好；用逻辑分析仪验证 CS / SCK / MOSI / MISO 四线时序 |
| **学会的标准** | 能说出 JEDEC ID 读出三种错误值分别对应什么问题——**这才是真正会用逻辑分析仪的表现** |

#### 3.15 ADC + DMA

| | |
| --- | --- |
| **学什么** | 分辨率与参考电压的关系（12 位 / 3.3 V → 最小分辨 0.8 mV）；单次 / 连续 / 扫描模式；规则组与注入组（了解即可）；**由定时器触发的同步采样** |
| **为什么重要** | 所有模拟量采集的基础。而"定时器触发 + DMA 搬运"这个组合，正是 BLDC FOC 电流环采样的同一套机制——现在学会，将来直接复用 |
| **常见追问** | ① 12 位 ADC 在 3.3 V 下的分辨率是多少 ② 采样时间为什么可调 ③ 为什么采样要由定时器触发而不是软件循环（要等间隔）|
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 8 项 |
| **怎么验证** | 用万用表量一个电位器的实际电压，同时串口打印 ADC 换算值，**误差应在几个 LSB 内**；进阶：改用定时器触发 + DMA，观察采样间隔是否稳定 |
| **学会的标准** | 能算出"要采 10 kHz、每个采样点 12 位，需要多大缓冲区、DMA 要搬多久"，并说明缓冲区不够时会怎样 |

#### 3.16 多传感器共总线

| | |
| --- | --- |
| **学什么** | 多个 I2C 器件共用一条总线的时序约束；为什么必须在同一时刻只有一个器件被访问 |
| **为什么重要** | 它是从"点灯级"走向"系统级"的第一步。更重要的是：**它会让总线冲突问题真实地暴露出来**——而这正是后面引入互斥量的现实依据。没有亲历过这个问题的，写 RTOS 时只会照抄"用互斥量保护总线"，答不出为什么 |
| **常见追问** | "多个任务都要读 I2C 传感器，会出什么问题？"——总线被抢占导致时序错乱、读到错误数据或 HAL 返回 BUSY |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §04 打卡表第 9 项 |
| **怎么验证** | 四个传感器（温湿度 / 气压 / 光照 / IMU）全挂在一条 I2C 上，都能稳定读到正确数据；**记录在裸机轮询方式下是否出现读出异常值**，把这现象记进调试日志——它是 W5 引入互斥量的动机 |
| **学会的标准** | 能说出"裸机上为什么没出问题，进了 RTOS 反而可能出问题"——因为裸机是串行执行的，RTOS 引入并发后总线访问会被打断 |

### L2 FreeRTOS

#### 3.17 任务与调度

| | |
| --- | --- |
| **学什么** | 任务的四种状态（运行 / 就绪 / 阻塞 / 挂起）；优先级与抢占式调度；时间片轮转；`vTaskDelay` 与忙等的区别 |
| **为什么重要** | 从"顺序执行"到"并发执行"是思维方式的变化。答不出"任务状态"这一层，就还停留在"会调 API"的阶段 |
| **常见追问** | ① FreeRTOS 怎么做任务切换（PendSV 异常）② 为什么空闲任务优先级必须最低 ③ 相同优先级任务什么时候切换（时间片到或有更高优先级就绪）|
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §05 |
| **怎么验证** | 建两个不同优先级任务，各自翻转一个 GPIO，用逻辑分析仪观察执行时序；再把两个任务改成同优先级，观察是否轮转 |
| **学会的标准** | 能画出自己项目的任务状态转换图，并说清每个任务在什么条件下进入阻塞 |

#### 3.18 队列 / 信号量 / 互斥量 / 事件组 选型

| | |
| --- | --- |
| **学什么** | 四者各自解决什么问题、不能互换的原因；二值信号量与计数信号量的区别；递归互斥量 |
| **为什么重要** | **这是 FreeRTOS 面试问得最多、也最能拉开差距的一个问题。** 面试官问的不是"怎么用"，而是"这个场景该用哪个、为什么"。答"都行"等于没答 |
| **常见追问** | ① 队列和全局变量加锁的区别 ② 互斥量和二值信号量的本质区别（互斥量有优先级继承和所有者概念）③ 我要让 ISR 通知任务，用哪个（信号量或任务通知，不是队列）④ 事件组适合什么场景（多事件组合等待）|
| **怎么配** | CubeMX → Middleware → FREERTOS → Queues / Semaphores / Mutexes / Event Groups |
| **怎么验证** | 在自己的项目里**各用一次**：采集任务与处理任务之间用队列传数据；I2C 总线用互斥量保护；中断通知任务用信号量；说出每一处为什么不用另一种 |
| **学会的标准** | 给定任意一个任务间通信场景，能在 5 秒内说出用哪个机制 + 一句理由 |

#### 3.19 优先级反转与优先级继承

| | |
| --- | --- |
| **学什么** | 优先级反转怎么产生（高优先级任务等被低优先级任务占用的资源，而低优先级任务又被中优先级任务抢占）；优先级继承怎么缓解；**它和优先级天花板、死锁的区别** |
| **为什么重要** | 这是实时系统里最经典的一个问题，也是 FreeRTOS 面试的必问题。而且它是"为什么互斥量不能换成二值信号量"的答案 |
| **常见追问** | ① 举一个优先级反转的具体例子 ② 优先级继承能完全解决吗（不能，只缓解）③ 死锁的四个必要条件 ④ 为什么不要在持有互斥量时做长耗时操作 |
| **怎么配** | 无需配置，是机制理解 |
| **怎么验证** | **动手复现**：三个任务（低 / 中 / 高优先级）+ 一个被低优先级持有、高优先级要用的资源，故意在持锁期间做长延时，用串口打印任务切换顺序，观察高优先级任务被中优先级任务间接阻塞；再把互斥量换成二值信号量，观察现象变化 |
| **学会的标准** | 能用自己项目的真实任务名，口述一个完整的优先级反转时序图，并说清哪一步是继承起作用的时刻 |

> **这是本手册里最值得花时间的一个知识点。** 能复现并讲清优先级反转，比多做两个外设的区分度高得多。

#### 3.20 中断安全 API（FromISR）与临界区

| | |
| --- | --- |
| **学什么** | 为什么中断里只能调 `...FromISR` 版本；`pxHigherPriorityTaskWoken` 参数的作用；`taskENTER_CRITICAL()` 与关中断的区别与代价 |
| **为什么重要** | 用错版本的 API 会直接死机或偶发异常。而这属于"看起来能用、实际上随时会炸"的问题——最难排查的一类 |
| **常见追问** | ① 为什么中断里不能用带阻塞的 API ② `pxHigherPriorityTaskWoken` 为什么必须传、不传会怎样（不会立即切换，实时性变差）③ 临界区应该多长 |
| **怎么配** | 无需配置，是 API 使用规范 |
| **怎么验证** | 在 EXTI 中断里用信号量唤醒任务，验证任务确实被唤醒；把 `FromISR` 改成普通版本，观察是否死机（在安全的前提下试一次，加深印象）|
| **学会的标准** | 能说出"中断里我只做三件事：清标志、发通知、退出去"，并解释为什么 |

#### 3.21 栈溢出与堆管理

| | |
| --- | --- |
| **学什么** | 每个任务的栈是独立分配的；栈溢出的后果（踩到相邻内存、行为诡异）；`configCHECK_FOR_STACK_OVERFLOW` 的作用；`xPortGetFreeHeapSize()` 与栈高水位查询；五种 heap 方案的区别 |
| **为什么重要** | 栈溢出是嵌入式里最恶心的 bug 类型：现象随机、位置无关、极难复现。而它同时也是面试里"你踩过什么坑"的优质素材 |
| **常见追问** | ① 任务栈大小怎么定（先给大、跑起来后看高水位再缩）② 局部大数组为什么危险 ③ heap_1 到 heap_5 的区别，项目里该选哪个 |
| **怎么配** | CubeMX → FREERTOS，开 `configCHECK_FOR_STACK_OVERFLOW = 2`、开 `configUSE_TRACE_FACILITY` |
| **怎么验证** | 故意给某个任务配一个过小的栈，触发溢出钩子函数；然后查各任务栈高水位，把栈按实际用量调整到合理值并记录 |
| **学会的标准** | 能说出"我的每个任务栈多少、是怎么定出来的、余量多少"，而不是"默认值" |

### L3 应用层（项目驱动，不单独学）

#### 3.22 BSP / App 分层架构

| | |
| --- | --- |
| **学什么** | 分层原则：CubeMX 只负责 `Core/` 与 `Drivers/`，手写代码放 `BSP/`（硬件相关）与 `App/`（业务逻辑）；接口与实现分离 |

| **常见追问** | "你的代码怎么组织的？"——分层清晰 + 能说清"换一颗传感器要改几个文件"，是很有力的回答 |
| **怎么配** | 见 `00-CubeMX工程搭建指南.md` §06 |
| **怎么验证** | 换一个同类型但不同型号的传感器（比如换个温湿度模块），**验证只改 `BSP/` 层、`App/` 层不动** |
| **学会的标准** | 能画出自己项目的目录树，并说清每个目录的职责边界与依赖方向 |

#### 3.23 自定义串口帧协议

| | |
| --- | --- |
| **学什么** | 帧同步（帧头）、长度字段、校验（和校验 / CRC16）、状态机解析；**粘包与断帧怎么处理** |
| **为什么重要** | 这是"能写协议"的入门证明。面试里问"你怎么保证数据完整"时，能说出帧头 + 长度 + 校验 + 状态机这套，就跨过了"只会收发字节"的门槛 |
| **常见追问** | ① 为什么要长度字段（不定长）② 校验为什么通常覆盖长度字段（否则长度被改会越界读）③ 接受方怎么从字节流里找到帧头且不误判（帧头转义或双字节帧头）|

| **学会的标准** | 能拿纸笔画出帧格式，并逐字段说明为什么需要它；能讲清状态机的每个状态和转移条件 |

#### 3.24 LVGL 移植与界面

| | |
| --- | --- |
| **学什么** | 移植三要素（显示驱动注册、心跳 `lv_tick_inc`、`lv_timer_handler` 调用）；显示缓冲区大小与刷新性能的关系；界面与业务逻辑解耦 |

| **常见追问** | ① 为什么 `lv_timer_handler` 要放进独立任务或定时器里 ② 缓冲区大小怎么选（小缓冲分块刷 vs 大缓冲全屏刷）③ 界面刷新卡顿怎么定位 |

## 04 库的选择：HAL / LL / SPL

### 三代库的定位

| 维度 | SPL（标准外设库） | HAL（硬件抽象层） | LL（低层库） |
| --- | --- | --- | --- |
| **抽象层次** | 寄存器级薄封装 | 高度抽象、跨系列统一 | 介于两者之间，贴近寄存器 |
| **维护状态** | **已停止更新**（止于 F1/F4 等老系列） | 持续更新，ST 主推 | 与 HAL 同节奏，API 更稳定 |
| **CubeMX 支持** | 自 CubeMX v5.0（2018）起**已移除** | 原生支持，自动生成 | 支持，可生成轻量代码 |
| **新系列覆盖** | 对 H7 / U5 / WL / WB **无官方驱动** | 全覆盖 | 全覆盖 |
| **代码体积** | 小 | 大（含大量通用性检查） | 中 |
| **执行效率** | 高 | 相对低 | 接近 SPL |
| **跨系列移植** | 差（各系列 API 有差异） | **极好**（同一套 API 跨 F1/F4/H7） | 好 |
| **学习资料** | 国内教程、毕设、老项目大量使用 | 官方资源最强 | 相对少 |

### 结论：HAL 主线，寄存器懂原理，LL 备用

**为什么不专门学 SPL：**

- 最后维护止于 F1/F4 老系列，**没有安全补丁**，对 F7/H7/G0/U5 等新系列不提供官方驱动
- 2026 年用 SPL 开新项目，等于自愿放弃 CubeMX 的代码生成和 ST 的工具链支持
- 企业在建新项目基本不会再选它

**但必须"能读懂"：**

- 国内大量教程、课程设计、以及深圳不少在维护的老项目仍在用 SPL
- 而 **F103 恰好是 SPL 生态最重的芯片**——搜资料时必然会撞上
- 所以要求是：**看到一个 SPL 函数能大致知道它在干什么**（比如 `GPIO_Init()` 对应 HAL 的什么），不需要会写

> ⚠️ **硬规则：同一个工程里绝不能混用 SPL 和 HAL。**
> 两套库底层都在初始化同一批寄存器，冲突时行为完全不可预测（可能编译通过但运行时随机异常）。看到有人说"某些驱动用标准库写、其余用 HAL"——不要学。

**什么时候必须用 LL：**

对时序或代码体积敏感的场合，例如：

- 电机 FOC 的电流环，中断服务函数里每一微秒都要省
- 需要精确控制死区时间
- 需要极低延时的 GPIO 翻转（直接写 `BSRR` 比 HAL 快若干倍）

**这条对本项目的意义**：现在只要知道"有这么一层、需要时能切过去"，**不需要花时间**。等将来做电机控制类项目时再回到这里。

### 三层理解的具体标准

| 层次 | 要求 | 判断标准 |
| --- | --- | --- |
| **寄存器** | 懂原理 | 能说出 HAL 函数最终操作的是哪个寄存器、哪一位；能查参考手册 |
| **HAL** | 会开发 | 日常开发的主线，能不看例程写出常用外设的初始化与收发 |
| **LL** | 能切换 | 知道什么场景该用、怎么和 HAL 混用；不需要熟练 |

## 05 环境说明

### 结论：VSCode + STM32CubeMX 完全可行

**关键是把两件事分开看**：谁**生成工程**（改 `.ioc`、生成代码），谁**提供编译工具链**（GCC / CMake / Ninja / 调试器）。这两件事可以由不同工具承担，不必是同一个。

### 两条路线对比

| | **路线 A：CubeIDE 自带 VSCode 扩展** | **路线 B：独立 CubeMX + CubeCLT + 官方扩展** |
| --- | --- | --- |
| 组件 | STM32CubeIDE（含 CubeMX 功能、GCC、CMake、Ninja、OpenOCD、调试器）、VSCode + 扩展 | STM32CubeMX（独立）、STM32CubeCLT（工具链）、VSCode + `STMicroelectronics.stm32-vscode-extension` |
| 优点 | 一次装完，工具链全部由 ST 管理；调试走官方 ST-Link GDB Server，稳定 | 不依赖 CubeIDE；组件职责更清晰 |
| 缺点 | 依赖 CubeIDE 安装 | 要多装两个东西；配置项更多 |
| **建议** | ✅ **用这个** | 暂时不需要 |

**判断理由**：本方案已经跑通完整链路（CMake + Ninja + GCC + `compile_commands.json` + clangd + ST-Link GDB），这套写在简历上已经足够专业，再折腾另一条路线只是额外成本。

> **实际落地形态（2026-10-10 校准）**：真正在用的是**混合方案**——
> - **生成工程**：独立版 **STM32CubeMX 6.x**（配置 `.ioc`、Generate Code，工具链选 **CMake**）
> - **编译工具链**：**CubeIDE 安装目录自带**的 GCC / CMake / Ninja / OpenOCD / ST-Link GDB Server
> - **写代码**：VSCode + STM32Cube 扩展（`cube-cmake` / `stm32cube-ide-clangd` / `stlinkgdbtarget`）
>
> 换句话说：**工具链来自路线 A，工程生成来自路线 B**，而 CubeIDE 的界面几乎不用打开。
> 判断依据：工程里没有 `.project` / `.cproject`（不是 Eclipse 工程），`.settings/ide.store.json` 里写着 `"sourceType": "STM32CubeMX"`。

### 工程配置的正确形态（逐项）

| 文件 | 作用 | 是否提交到仓库 |
| --- | --- | --- |
| `*.ioc` | CubeMX 工程源文件。**没有它工程无法复现** | ✅ 必须 |
| `.mxproject` | CubeMX 的元数据（记住上次配置） | ✅ 提交 |
| `CMakeLists.txt` / `CMakePresets.json` / `cmake/` | 构建定义 | ✅ 提交 |
| `build/` | 构建中间产物与 `.elf` | ❌ 忽略 |
| `.vscode/settings.json` | 指定 `cube-cmake`、clangd 的查询驱动 | ✅ 提交（让 clone 下来就能编译） |
| `.vscode/launch.json` | 调试配置（ST-Link GDB Server） | ✅ 提交 |
| `.vscode/c_cpp_properties.json` | IntelliSense 指向 `compile_commands.json` | ✅ 提交 |
| `.clangd` | 指定编译数据库所在目录 | ✅ 提交 |
| `compile_commands.json`（在 `build/` 内） | 每个源文件的真实编译命令，供 clangd / IntelliSense 使用 | ❌ 由构建生成 |
| `.settings/` | CubeMX 的工程设置（`ide.store.json` 记录生成器与工具链） | ✅ 提交 |

> **一条容易被忽略的原则**：`.vscode/` 与 `.clangd` **应该提交**。它们决定别人（以及半年后的你）clone 下来能不能直接编译、能不能有代码跳转。把它们加进 `.gitignore` 是很常见的错误做法。

### 环境相关的三个常见坑

1. **工程路径不能含中文或空格**
   CMake / Ninja / GCC 在 Windows 上处理非 ASCII 路径有已知缺陷，症状是"找不到文件""编译出奇怪错误"。**代码工程一律放纯英文路径**（如 `D:\STM32\`），文档放哪都无所谓。

2. **`SYS → Debug` 必须设成 `Serial Wire`**
   留默认的话，第一次烧录后芯片的 SWD 口会被关闭，ST-Link 再也连不上（现象是 "No target connected"）。
   **已经锁了的恢复办法**：把 BOOT0 拉高后上电，用 STM32CubeProgrammer 执行 Full chip erase。

3. **`SYS → Timebase Source` 不要留默认的 SysTick**
   HAL 默认用 SysTick 做时间基准，而 FreeRTOS 也要用 SysTick —— 两者冲突会导致 `HAL_Delay` 卡死或时序异常。
   **这一条在裸机阶段就要改好**，等到引入 RTOS 再改会发现很多代码已经依赖了旧行为。
   **改成哪个定时器要看芯片**：STM32F407 有基本定时器，用 **TIM6**；STM32F103C8T6 属于**中容量**型号，**根本没有 TIM6/TIM7**（只有 TIM1~TIM4），用 **TIM4**。
   > 查证方法：看 CMSIS 头文件（`stm32f103xb.h`）里有没有 `TIM6_BASE` 定义，或直接看 CubeMX 时基下拉框里有没有 TIM6。**看不到不是软件问题，是硬件没有。**
   附带限制：改完后任何优先级比时基中断更高的 ISR 里都不能调用 `HAL_Delay()`（`HAL_IncTick()` 执行不到，会死等）。注意「优先级数值 ≥ 5 的中断里不能调 RTOS API」是 **FreeRTOS 自己的规则**，别混为一谈。

### 用 AI 辅助时的固定提问模板

嵌软场景里，AI 最容易犯的错是**不知道你用的是哪套库、哪个型号**，于是混着给你 SPL 和 HAL 的 API。每次提问带上这句话，输出质量会立刻不同：

```
芯片 STM32F103C8T6（或 STM32F407），HAL 库，CubeMX 生成，
CMake + Ninja 构建（工具链来自 CubeIDE 安装），VSCode + STM32Cube 扩展。
```

## 06 Git 与版本管理

### 6.1 为什么这个要单独成章

- **JD 里会直接写"熟悉 Git"。** 它是嵌入式岗位少有的、明确写进任职要求的软技能
- 面试官会问"你的代码怎么管理的"——这题答不好，前面项目讲得再细也会被扣分
- **公开仓库是"没有实验室经历"时的替代品**：代码、调试日志、设计文档摆在那里，比任何自述都可信
- 一个具体的加分点：能说出"**我的 commit 是按功能切的粒度，不是按天切的**"

### 6.2 首次配置（先自检，再配置）

**第一步永远是自检：**

```bash
git config --global --list
```

如果输出为空（或者只有 `core.xxx` 这类系统项而没有 `user.name`），说明身份从未配置过。

**为什么必须最先配这个**：Git 在提交时会用 `user.name` / `user.email` 写进 commit 的 author 字段。如果没配，Windows 上它会用系统账号名自动编造一个身份——**而一旦提交，这条信息就永久留在了历史里**，后面改起来很麻烦（要 rebase 重写历史）。

```bash
git config --global user.name  "你的姓名（拼音或英文）"
git config --global user.email "你的 GitHub 账号邮箱"
```

> `user.email` **必须与 GitHub 账号关联的邮箱一致**，否则提交不会归到你的账号下，GitHub 上显示不出贡献记录。

**其余几项建议一并配置：**

```bash
# 默认分支名改成 main（与 GitHub 一致，避免新建仓时提示不一致）
git config --global init.defaultBranch main

# Windows 换行符处理：提交时转 LF、检出时转 CRLF
# 嵌入式常跨平台（Windows 开发 + Linux 构建），不设这个会出现"整个文件都变了"的假 diff
git config --global core.autocrlf true

# 中文文件名在 git status 里正常显示（否则会显示成 \344\270\255 这种转义）
git config --global core.quotepath false
```

配置完再跑一次 `git config --global --list` 确认。

### 6.3 认证方式：用 SSH key，不要用 PAT

**一条时效性很强的信息**：GitHub 的 **classic PAT（个人访问令牌）自 2026 年 3 月 1 日起被逐步淘汰**。网上大量中文教程还在教"生成 PAT 当密码用"，**已经过时了**。替代方案是 fine-grained PAT，但它按组织授权、需要定期更新，用起来更麻烦。

**推荐直接用 SSH key**，一次配置长期有效：

```bash
# 1. 生成密钥（一路回车即可，密码短语可留空）
ssh-keygen -t ed25519 -C "你的 GitHub 账号邮箱"

# 2. 查看公钥并复制全部内容
cat ~/.ssh/id_ed25519.pub

# 3. 打开 GitHub → Settings → SSH and GPG keys → New SSH key
#    Title 随便填（如 "宿舍台式机"），Key 粘贴上一步内容

# 4. 验证（应输出 "Hi <你的用户名>!"）
ssh -T git@github.com
```

之后所有 `clone` / `push` / `pull` 都不再需要输密码。

> 记住一件事：`~/.ssh/id_ed25519` 是**私钥，绝不外传**；只有 `.pub` 结尾的公钥可以粘贴出去。

### 6.4 心智模型：四区三态

理解这个模型，Git 的 90% 命令都不用背：

```
工作区                暂存区              本地库              远程库
(你编辑的文件)   →   (准备提交的内容)  →  (已提交的历史)  →  (GitHub)
                add                 commit            push
        ←────────────────────────────────────────
                      pull / fetch
```

用拍照类比：

| 动作 | 类比 |
| --- | --- |
| `add` | 把想拍的东西摆进取景框（选择要提交哪些改动） |
| `commit` | 按下快门，得到一张不可修改的照片（历史记录） |
| `push` | 把照片上传到云相册（GitHub） |
| `pull` | 从云相册拉回别人拍的新照片 |

**关键认知**：**commit 之后的东西不是不能改，而是改了会留下痕迹。** 这正是版本控制的价值——你能看到"什么时候改的、为什么改"。

### 6.5 场景化命令（按"我要做 X"查）

**① 把已有工程第一次推上 GitHub**

先在 GitHub 网页上建一个**空仓库**（不要勾选 "Add a README"），然后：

```bash
cd /d/STM32/stm32-iot-node
git init
git add .
git status                      # ← 关键一步：提交前先看，确认没混进 build/ 或大文件
git commit -m "chore: 初始提交"
git remote add origin git@github.com:<用户名>/stm32-iot-node.git
git push -u origin main
```

**② 日常提交**

```bash
git status                      # 看有哪些改动
git diff                        # 看具体改了什么内容
git add <文件>                   # 提交指定文件（推荐，而不是 git add .）
git commit -m "feat(adc): 定时器触发的同步采样"
git push
```

**③ 看历史**

```bash
git log --oneline --graph --all # 一行一条 + 分支图
git show <commit-id>            # 看某次提交的完整改动
git diff <commit1> <commit2>    # 两次提交之间差了什么
```

**④ 撤销未提交的改动**

```bash
git restore <文件>               # 丢弃工作区的修改（危险：改不回来）
git restore --staged <文件>      # 只从暂存区撤出，保留文件内容
```

**⑤ 改最后一次 commit 的信息**

```bash
git commit --amend -m "新的提交信息"
```

> 只在**没有 push 过**的情况下用。已推送的提交不要 amend。

**⑥ 回退到某个版本**

```bash
git revert <commit-id>          # 安全：生成一个反向提交，历史保留
git reset --soft <commit-id>    # 退回提交前状态，改动仍在暂存区
git reset --hard <commit-id>    # 危险：改动全部丢失
```

**⑦ 误操作后的最后一道保险**

```bash
git reflog
```

这个命令记录**所有 HEAD 的移动**，包括 reset、rebase、checkout。**几乎任何"我把东西搞丢了"的场景都能靠它找回**。记住它——这是 Git 里最救命的命令。

**⑧ 忽略已经提交过的文件**

`.gitignore` 对**已经被跟踪的文件无效**。必须先移除跟踪：

```bash
git rm --cached <文件>          # 从索引移除但保留本地文件
# 然后把它加进 .gitignore
```

**⑨ 处理冲突**

```bash
git pull                        # 冲突会标记在文件里
# 手动编辑，解决 <<<<<<< ======= >>>>>>> 标记
git add <冲突文件>
git commit
```

### 6.6 `.gitignore` 怎么写（嵌入式特有）

**必须排除：**

```gitignore
# 构建产物
build/
*.o  *.obj  *.elf  *.bin  *.hex  *.map  *.lst  *.d

# CubeMX 临时文件
mx.scratch
Backup/
/Core/Backup/

# Python 上位机
__pycache__/
*.py[cod]
.venv/
data/*.csv
data/*.log

# 凭据（重要）
wifi_credentials.h

.env

# 系统
.DS_Store
Thumbs.db

```

**必须提交（不要忽略）：**

| 文件 | 原因 |
| --- | --- |
| `*.ioc` | 没有它工程无法复现 |
| `.mxproject` | CubeMX 元数据 |
| `CMakeLists.txt` / `CMakePresets.json` / `cmake/` | 构建定义 |
| `.vscode/settings.json`、`launch.json`、`c_cpp_properties.json` | 决定 clone 下来能否直接编译调试 |

**两个最常见的错误：**

1. **把 `build/` 提交进去** —— 仓库迅速膨胀到几十 MB，且每次构建都产生大量无意义 diff
2. **把 `.ioc` 排除掉** —— 别人 clone 下来只有一堆 C 文件，无法重新配置外设，工程等于不可复现

### 6.7 commit message 规范

推荐 Conventional Commits 格式：

```
<类型>(<范围>): <描述>
```

| 类型 | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 重构，不改变行为 |
| `chore` | 构建、依赖、杂项 |
| `test` | 测试相关 |

**对照示例：**

| ❌ 坏 | ✅ 好 |
| --- | --- |
| `update` | `feat(i2c): 接入 SHT30 温湿度采集` |
| `改了点东西` | `fix(uart): 修复 DMA 接收丢帧，改用空闲中断 + 环形缓冲` |
| `1111` | `fix(i2c): 修正 7 位地址未左移导致读不到器件` |
| `完成` | `refactor(bsp): 传感器驱动按 BSP 分层抽出，App 层不再直接碰 HAL` |

**为什么这在面试里有用**：面试官翻你的仓库时，`git log` 是第一个看的地方。一个信息清晰的提交历史，能直接证明你的工程习惯——而且它顺便帮你准备好了"踩过什么坑"这个必问题的答案。

### 6.8 分支策略（个人项目最小集）

个人项目用两条规则就够了：

- **`main` 保持可用**：任何时刻 `main` 上的代码都应该能编译通过
- **大改动开分支**：`feature/lvgl-port`、`feature/freertos-refactor`，做完合并回 `main`

```bash
git switch -c feature/lvgl-port    # 开分支
# ... 开发 ...
git switch main
git merge feature/lvgl-port        # 合并
git branch -d feature/lvgl-port    # 删掉已合并的分支
```

> **不要引入 Git Flow。** 那套（develop / release / hotfix 多分支）是为多人协作和定期发布设计的，个人项目用它是纯粹的负担。

### 6.9 GitHub 上的呈现

| 要素 | 怎么做 | 为什么 |
| --- | --- | --- |
| **README** | 写清项目背景、功能、架构图、BOM 与选型理由、实测数据 | 别人打开仓库第一眼看的就是它 |
| **LICENSE** | 加一个 MIT 许可（一行的事） | 没有 License 的仓库会被认为"只是个人练习" |
| **Release** | 把编译好的 `.hex` / `.bin` 作为附件发布 | 避免把二进制塞进 git 仓库，同时方便别人直接下载试用 |
| **Issues** | 用 Issue 记 TODO 和已知问题 | 展示你有在维护，而不是传完就不管 |
| **GitHub Pages** | `Settings → Pages → Source = main 分支 /docs 目录` | 把 `docs/` 下的文档变成在线站点，手机上也能看 |

> **Pages 的一个重要限制**：站点是**公开**的。即使从私有仓库发布（需要 Pro 账号），Pages 站点默认仍然对所有人可见。所以 **Pages 只放技术文档，不放任何个人隐私信息**。

### 6.10 双仓的边界规则

**核心规则：作品进公开仓，计划进私有仓。**

| 可以公开 | 不要公开 |
| --- | --- |
| 固件代码、BSP/App、原理图、PCB 截图 | 含手机号、邮箱、身份证号的个人材料 |
| 调试日志：踩过的坑与解决过程 | 个人计划、清单、联系人信息 |
| 技术笔记、选型理由、通信协议说明 | 薪资、合同等商业敏感信息 |
| 学习笔记、命令速查表 | 私人记录与复盘 |

**判断标准很简单**：这段文字是**证据**还是**过程**？

- "用逻辑分析仪抓到 I2C 的第 9 个时钟有 ACK" → 证据，公开是加分
- "LED 先点亮就行，显示屏留到第 6 周再说" → 过程，公开很难看

## 07 资源使用指南

### 7.1 四套资源的定位（按阶段用）

| 资源 | 什么时候用 | 怎么用 |
| --- | --- | --- |
| **正点原子** | 外设入门阶段（主线） | **按需检索，不要从头刷完**。直接跳到你要的那个外设 |
| **野火** | 某个知识点讲不透时作补充 | 讲原理更系统，代码分层更规范 |
| **硬汉 / 安富莱** | 进入 FreeRTOS 阶段后 | 讲到源码级，啃内核的最优解 |
| **官方参考手册** | 全程，尤其是 HAL 行为不符预期时 | 唯一权威，面试说"查过参考手册"很有说服力 |

> ⚠️ **最重要的一条：正点原子的教程有 HAL 库版和标准库版两套。**
> 网上搜到的老视频和老文章大量是标准库版。**必须明确选 HAL 库版本**，搜错版本会浪费大量时间（代码对不上、函数名不存在）。
> 搜索时带上 `HAL` 关键词，例如"正点原子 STM32F103 HAL 库开发指南"。

### 7.2 官方手册怎么查

| 手册 | 对应系列 | 用途 |
| --- | --- | --- |
| **RM0008** | STM32F1 | F103 的参考手册（寄存器定义、外设工作原理） |
| **RM0090** | STM32F4 | F407 的参考手册 |
| 数据手册（Datasheet） | 各型号 | 引脚定义、电气参数、封装 |
| 器件手册 | 各传感器 / 外设芯片 | 寄存器表、通信时序、地址 |

**查参考手册的方法**：`Ctrl+F` 搜寄存器名（如 `BSRR`），直接跳到寄存器描述那一节。不需要通读——手册是字典，不是教材。

### 7.3 三种常见的错误用法

| 错误用法 | 为什么错 | 正确做法 |
| --- | --- | --- |
| **从头刷完一整套视频教程** | 一套教程几百集，刷完要几个月，而且刷的过程中没有任何产出 | 按需检索：学到哪个外设，只看那一节 |
| **只看视频不动手** | 嵌入式是手上功夫，看会 ≠ 做会。视频里顺利的接线，你手上要接三次 | 每个知识点都必须有一个可观察的现象 |
| **卡住了自己死磕一周** | 时间成本极高，而且往往卡的是一个极小的点 | **硬规则：同一个问题卡超过 24 小时必须去问**（论坛、AI、同学、老师都行） |

### 7.4 AI 辅助的正确姿势

**固定提问模板**（每次带上）：

```
芯片 STM32F103C8T6（或 STM32F407），HAL 库，CubeMX 生成，
CMake + Ninja 构建（工具链来自 CubeIDE 安装），VSCode + STM32Cube 扩展。
```

**为什么必须带**：AI 不知道你的软硬件环境时，会混着给你 SPL 和 HAL 的 API——而这两套绝对不能混用。

**AI 适合做的：**

- 解释一段报错信息的含义
- 讲清一个概念（"环形缓冲区解决了什么问题"）
- 审查你的代码思路有没有明显问题
- 帮你查寄存器位定义、外设工作流程

**AI 不适合做的：**

- 直接生成整个工程让你粘贴（你会失去排查能力）
- 回答"我的代码为什么不工作"（信息不足时它会编）
- 替代你读参考手册

> **一条原则：AI 帮你理解，但不替你理解。** 面试官问"这段代码你怎么写的"，答"AI 生成的"是零分。

### 首次配置（只做一次）

```bash
git config --global user.name  "你的姓名"

ssh-keygen -t ed25519 -C "邮箱"          # 生成 SSH key，一路回车
cat ~/.ssh/id_ed25519.pub               # 复制 → GitHub → Settings → SSH keys
ssh -T git@github.com                   # 验证，应输出 Hi <用户名>!
```

### 三个最容易忘的点

1. **`.gitignore` 对已跟踪文件无效** → 先 `git rm --cached <文件>`
2. **`git add .` 之前先 `git status`** → 确认没混进 `build/`、大文件、敏感信息
3. **`git reflog` 几乎能救回一切** → 别慌，先跑它
