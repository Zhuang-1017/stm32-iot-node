# 调试日志

> **每个踩过的坑记一条。** 这不是流水账，是面试时"你遇到过什么困难、怎么解决的"这个必问题的答案库。

---

## 为什么要记

嵌入式面试里最容易被问倒的一题是：

> "这个项目里你遇到过什么困难？怎么解决的？"

大多数人答不上来 —— 因为当时解决了就过去了。但**面试官问的不是"你有多惨"，是"你的排查方法论"**：你怎么定位问题、排除干扰、最终找到根因。

一条好的调试记录能让面试官看到三件事：你真的动过手、你有系统的排查思路、你能把技术问题讲清楚。

---

## 模板

每条日志一个文件，命名 `YYYY-MM-DD-简短描述.md`：

```markdown
# <一句话描述现象>

**日期**：2026-XX-XX
**涉及**：<外设 / 模块 / 芯片>

## 现象

<观察到什么。要具体：错误码、串口输出、波形表现、复现条件>

## 排查过程

1. <先怀疑什么，怎么验证的，结果如何>
2. <再怀疑什么……>
3. <最后定位到>

> 排查过程比结论更重要 —— 不要只写最终答案。

## 根因

<为什么会这样。讲清机制，不只说"改了这个就好了">

## 解法

<改了什么。如果改了代码，贴关键 diff>

## 如果重来

<有没有更快的定位路径 / 更稳妥的设计>
```

## 几个"值得记下来"的信号

遇到下面任意一种情况，立刻记：

- 排查超过 30 分钟后才找到的问题（不管多小）
- 现象与直觉相反（"按道理不该这样"）
- 同一类问题第二次出现
- 看起来是 A 的问题、实际是 B 造成的（比如"串口乱码"其实是时钟配错）
- 硬件问题伪装成软件问题（或反过来）
- 用逻辑分析仪 / 示波器看到与预期不符的波形
